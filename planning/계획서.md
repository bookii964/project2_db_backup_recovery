## 1. 배경·문제
- project_1에서 정제한 데이터 5종을 PostgreSQL에 적재했다. 결과는 테이블 6개, 930,554행, 제약조건 67개(PK 6, FK 6, CHECK 26, NOT NULL 29)다. 근거: [project_1 README](../../project_1/README.md) 2절
  - project_1 README는 NOT NULL을 CHECK에 합쳐 "CHECK 55"로 적었다. 이 프로젝트는 둘을 나눠 적는다. 조회하는 카탈로그에 따라 NOT NULL이 CHECK에 섞이거나 빠지기 때문이다(맥락노트 3절).
  - 환경: 로컬 PostgreSQL 16.15, DB `portfolio_db`, 스키마 `portfolio`, 서비스 이름 `postgresql-x64-16`. 근거: [적재가이드](../../project_1/04_reports/6단계_DBeaver_적재가이드.md), `pg_dump --version`·`sc query` 실행 결과
- 이 DB에는 이 계획에 따라 **직접 만들고 검증한 백업이 아직 없다.** 실수로 DROP이나 DELETE를 하면 정제 파이프라인(스크립트 22개)을 처음부터 다시 돌려야 한다.
- 지원 직무(DBA·데이터 엔지니어)는 백업·복구 역량을 요구하며, 특히 "백업 성공 상태만 확인하지 않고 **복구 가능성을 검증한 경험**"을 강조할 만한 경험으로 꼽는다. 근거: [DBA_데이터엔지니어_지원역량_정리.md](../../job_research/DBA_데이터엔지니어_지원역량_정리.md) 40~47행, 235행
- 따라서 실제 규모의 데이터로 백업·복구 절차를 직접 수행하고 수치(소요 시간, 용량, 정합성)로 증명해 두려 한다. 동시에 SQL·Bash·Python을 직접 작성하며 데이터 엔지니어 기본기를 키운다.
- 실무 DB 서버는 대부분 리눅스이고 백업 스크립트도 셸로 작성하는 경우가 많다. 그래서 자동화는 **Git Bash에서 Bash 스크립트로** 작성한다. Python은 Bash로 처리하기 번거로운 지표 집계와 보고서 표 생성에만 쓴다(3-6절).
- 2026-11-17에 단계 1을 마쳤으나 AI가 코드를 대신 작성해 과정을 직접 경험하지 못했다. 그래서 2026-11-20에 처음부터 다시 시작하고, AI 사용 원칙을 정했다(3-7절).
- project_2는 원래 비즈니스 분석 프로젝트로 계획했지만 취소했다. 2026-11-17에 분석 계획서를 삭제하고 project_2를 이 작업으로 바꿨다(9절 참고).

## 3. 범위
### 3-1. 포함
- 논리 백업: `pg_dump` 전체 DB / 테이블 단위, 형식 비교(plain SQL과 custom). 용량·시간 비교
- 복구: `pg_restore`로 전체 복구, 단일 테이블 복구, 병렬 복구(`-j`) 시간 비교
- 검증: 행 수, 제약조건, 체크섬, FK 무결성, 집계 결과를 SQL로 뽑고 Bash에서 `diff`로 비교
- 장애 시나리오 실습 (3-3절의 실습 환경 원칙을 따른다)
  1. `orders` 테이블 DROP → 단일 테이블 복구 (FK 의존성 처리 포함)
  2. 잘못된 WHERE 조건으로 DELETE 실행 → 백업에서 해당 행만 되살리기
  3. 백업 파일 손상·불완전 → 복구 전 무결성 점검으로 미리 잡아내기
- 물리 백업과 PITR: WAL 아카이빙 설정 → `pg_basebackup` → 잘못된 DELETE → 직전 시각으로 시점 복구
- Bash 백업 자동화 스크립트와 보관 정책(논리 백업, 베이스 백업, WAL)
- 실행 지표 기록(Bash)과 지표 요약 보고서 생성(Python)
- 절차서, 결과 보고서, 학습 노트(백업 종류, RPO·RTO 개념, Bash 문법, Python 데이터 처리)

### 3-4. Git Bash 실행 환경 규칙
Windows에서 Bash를 쓸 때 생기는 문제를 막기 위해 아래를 지킨다. 설정은 단계 1에서 한다.

| 규칙 | 이유 |
|---|---|
| 비밀번호는 `%APPDATA%\postgresql\pgpass.conf`에 두거나 `PGPASSFILE`로 위치를 지정한다. 스크립트·로그에는 넣지 않는다 | Windows의 PostgreSQL은 `~/.pgpass`를 읽지 않는다 |
| 접속 정보(호스트·포트·사용자·경로)는 `config/env.sh` 한 곳에 두고 스크립트가 `source`로 읽는다 | 값을 바꿀 때 한 곳만 고치면 된다 |
| 경로는 `C:/...` 형식으로 쓰고, PostgreSQL 명령에 경로를 넘길 때는 `MSYS_NO_PATHCONV=1`을 붙인다 | Git Bash가 `/`로 시작하는 인자를 Windows 경로로 바꿔 `pg_ctl -D` 같은 명령이 깨질 수 있다 |
| `.sh` 파일 줄바꿈은 LF로 고정한다 (`.gitattributes`에 `*.sh text eol=lf`) | CRLF면 `$'\r': command not found` 오류가 난다 |
| `PGCLIENTENCODING=UTF8`을 설정한다 | psql 오류 메시지와 로그의 한글이 깨지는 것을 이전 시도(2026-11-17)에서 확인했다 |
| 모든 스크립트는 `set -euo pipefail`로 시작한다 | 중간 단계가 실패하면 그 자리에서 멈춰, 실패한 백업을 성공으로 착각하지 않게 한다 |
| `archive_command`는 Windows `copy` 명령으로 쓴다 | 이 명령은 PostgreSQL 서비스가 cmd.exe로 실행하므로 Bash 문법이 통하지 않는다 |
| 서비스 재시작(`net stop/start postgresql-x64-16`)은 Git Bash를 **관리자 권한**으로 열어 실행한다. 재시작이 끝나면 관리자 창을 바로 닫는다 | 서비스 제어는 관리자 권한이 필요하다. 다른 스크립트까지 관리자 권한으로 돌지 않게 한다 |

### 3-6. Bash·Python 역할 분담
**판단 기준**: 이 프로젝트의 모든 작업은 Bash만으로 할 수 있다. Python은 Bash보다 분명히 효율적인 곳에만 쓴다.

| 작업 | 도구 | 판단 근거 |
|---|---|---|
| 백업·복구·인스턴스 제어 | Bash + PostgreSQL 명령줄 도구 | `pg_dump`·`pg_restore`·`pg_ctl`은 명령줄 도구라 Bash가 가장 직접적이다. Python으로 감싸면 호출 코드만 늘어난다 |
| 정합성 값 계산 (행 수·체크섬·집계) | SQL | DB 안에서 계산해야 93만 행을 밖으로 옮기지 않는다 |
| 원본·복구본 결과 비교 | Bash `diff` | 결과가 텍스트 파일이라 `diff` 한 번이면 된다 |
| 지워진 행 찾기·되살리기 (시나리오 2) | SQL + `psql \copy` 파이프 (Bash) | 두 DB 사이 행 이동은 한쪽에서 `\copy ... to stdout`, 다른 쪽에서 `\copy ... from stdin`을 파이프로 이으면 된다. Python(psycopg)으로도 가능하지만 코드만 길어진다 |
| 실행 지표 기록 | Bash (`lib.sh`가 `logs/metrics.csv`에 한 줄씩 추가) | 각 스크립트가 끝나는 시점에 바로 남겨야 한다 |
| 지표 집계·보고서 표·차트 | Python (pandas, matplotlib) | 그룹별 평균, 비율(plain 대비 custom, 단일 대비 `-j 4`) 계산과 마크다운 표 생성은 awk로도 되지만 코드가 길고 고치기 어렵다. 차트는 Bash로 만들 수 없다. "로그 → 정형 데이터 → 리포트"는 데이터 엔지니어의 대표 업무이기도 하다 |
